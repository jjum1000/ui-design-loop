# Agent prompt templates

Common header for every prompt (do not leave it out):
```
You own the <stage> stage for <screen>. Write in <the user's language>; code and file names in English.
Background: <one line about the game and the screen>, <goal of this stage>.
Inputs (read-only): <list of paths, relative to the Unity project root>
User decisions (final): <list>
Tasks: <numbered list>
Outputs (write only these paths): <path> - sections: <list>
Acceptance criteria: <measurable list>
Forbidden: editing the Unity project, committing, the Playwright MCP browser, editing frozen files. Write files with the Write tool (no Bash heredocs).
When done, report briefly: <report items>
```

## S0
- **systems-designer**: feature table (ID, information, action, evidence file:line, frequency, lock), state machine, formulas (in code order, with caps), summary of real preset values, table of values that differ from code defaults, unknowns, UX notes. `fixture.json`: about 5 states with real strings and real computed values, plus a `calc` field.
- **Explore**: per server request, when it is called and its inputs/outputs; state checks; client computation vs. server values; "can start / can act" checks; locks; result handling; notifications; original localization keys of on-screen strings; preset-vs-code mismatches. About 1,500 words with file:line.

## S2
- **art-director**: 3-5 reference screens (look at the renders), rules for color, typography, shape, components and skeleton (evidence = screen slug + node or token ID), Do/Don't, list of required kit elements. "No guessing; mark unknowns."
- **general-purpose**: a `build_kit.py` that produces `kit.css` (tokens, ColorTint `--btn-*`, 9-slice, `@font-face`), assets (copies of the originals, atlas rects cut out), `components.md` (a table mapping each kit element to its Unity template slug, usage counts, 9-slice and notes), a specimen page, and a headless check.

## S1a Flow and reference flow
- **ux-designer**: the confirmed main flow from the spec (tasks, steps, frequency).
- **general-purpose**: candidate existing screens with a similar flow. If `ui-audit/data/app-flow.json` exists, follow `next` links to trace the real flow; list the templates used at each step (`data/layout/screen/*.json`); only screens with `cleanReference=true` in `Docs/ui-design-system/screens.jsonl`. Similarity is scored on "the shape of the flow per step" as the first axis (fix the axes before scoring). Evidence = render crops.

## S1b Wireframe
- **ux-designer**: on the layout of the chosen reference screen: task definition, changes vs. the reference layout (with reasons), hierarchy and placement table (every F item), interaction spec, 2+ alternatives for contested points with a recommendation, `wire.html` (follows the page contract, data inline). Blank-slate concept comparisons only when there is no reference flow.
- **game-designer (adversarial)**: core loop, reward peaks, fun of decisions, motivation behind locks, recomputed tap counts for the mastery path, omissions. Grouped by severity, with a numbered list of change requests.

## S3-0 scene composition -> S3 skinning (the same agent continues)

- **general-purpose x1-2 (strict, proposal)**: add the following to the common header verbatim.
  - **First action: load `frontend-design:frontend-design` with the Skill tool.** Apply its principles (spatial composition, whitespace, density, detail) to **this project's existing scene composition**. Do not invent a new aesthetic; match the reference renders.
  - **The wireframe is topology only**: "Take from the wireframe: list of regions, order, flow, hierarchy, interactions, states. Do not take: coordinates, box shapes, panel borders, widths, number of panels. The grey-box placement is a diagram that explains the flow." (Never write "keep the wireframe structure".)
  - **Phase 1, S3-0 (before building)**: open 2-3 reference renders and choose them (one-line reason each); write a one-line concept yourself; decide panel count, position, off-screen flow, left-side composition, tabs and header strip from the "Scene composition" precedents in `precedents.md`; give every block coordinate a **content-based rationale** (for example "6 request cards x 82 + header strip -> panel body height"). **Core component precedent check** (list row and its container / tab art and alignment / thumbnails / selection marker / action button row / popup frame; each one as a precedent render crop next to the plan at the same scale). Write `composition.md` and `composition-sheet.png` (references vs. planned blocks + a row of component crop comparisons, generated by a script), then **stop and report**. No building before the orchestrator gate passes.
  - **Phase 2, S3 (after the gate, same agent)**: build according to the composition. An element mapping table, if any, is **reference material** (composition wins on conflict). Reuse the wireframe JS, add `data-template`/`data-new`/`data-area` attributes, resolve wireframe leftovers.
  - **Acceptance criteria**: `shoot.py` PASS, zero scroll, **`shots/variant-x/ref-compare.png`** (top = 2-3 reference renders, bottom = 2-3 representative states) produced and inspected, with a pass/partial table per composition precedent in the changes document; weaknesses self-reported. "Measurement PASS = done" is false.
  - For a reproduction experiment, **do not give** earlier variants (other variants' code or shots) or the element mapping table. For a revision of the chosen variant, give its code plus a delta list.
  - Turn budget: "When the evidence is in, write the file first, then refine."

## S4 review
- **ux-designer**: flow drift vs. the wireframe, tap-count regressions, lost information, how contested points were implemented.
- **art-director**: **inputs = reference renders (`previews/layout/screen/*.png`) + variant shots + `ref-compare.png` only.** Judge first: scene composition (panel count, position, left side, tabs, header strip, body), consistency with existing screens, conflicts in color meaning. Only **after** writing that verdict to a file, open the deviations and decision documents for cross-checking and mark each deviation adopt/hold/reject. Never give the mapping table or a "kit consistency" premise as input.
- **general-purpose (measured accessibility)**: headless: bottom 20 touch targets, font distribution, WCAG contrast (linearized, alpha-composited), color independence, motion, tooltip-only information.
- **unity-ui-specialist**: check every slug and sprite against the data, difficulty of translating CSS to uGUI, 9-slice, TMP, list virtualization, re-estimate deviation costs, prefab cautions (never unpack `Completely`).

## Alignment audit
- **general-purpose**: every `data-new` kind -> 0-3 candidate templates (size, structure, usage; compare renders directly) -> evidence images (element crop vs. template render) -> preliminary class 1/2/3/4 + confidence + change spec for the next revision.
- **ux-designer**: attention budget per state, difference vs. measurement (`attention.py`), information audit (keep/demote/remove/emphasize/add), correction instructions.
- **art-director**: finalize classes, numeric visual rules (type scale, emphasis, motion budget, attention levers, empty states), merged instructions.
- **game-designer**: effect of the attention budget and information audit on motivation, reward exposure principles.
- **unity-ui-specialist**: feasibility of classes 1/2 (whether a shared prefab must change, number of affected usages), constraints of shared screens, plan for class 3.
